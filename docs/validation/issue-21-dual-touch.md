# #21 双指断触诊断进度

用户报告：浮动摇杆持续滑动时，另一只手点按放弹会使左侧断触，角色停止，必须重新操作左手。起点为 `38debe6`；用户于2026-10-27明确授权独立无头浏览器和“浏览器触控输入”回归边界。当前没有确认手机根因，也没有宣称修复。

## 已验证

- 原代码在独立 Chrome、Edge 的960×400横屏中，原生双指按下/抬起、左手持续拖动和连续点按均保持方向；Chrome的412×915竖屏及750ms长按也未复现。最初脚本曾把左手当作右手抬起，该脚本错误已纠正，不能当作缺陷复现证据。
- `pnpm test:browser-touch` 经真实页面设置、开局、CDP原生触控和公开页面诊断验证：固定/浮动两模式下右手放弹及松开，左手不需再移动即可继续推动角色；左手释放清空方向；真实浏览器取消清空两控件。检查方向、浮动中心不变和实际角色位置前进，而非只测输入模块。
- 浮动测试同时核对触控诊断报告包含原生取消、放弹目标和右向输入；固定测试核对普通验收模式不记录触控事件。诊断入口曾遮挡新版菜单设置，现移到菜单左下方，端到端操作可直接点击设置。

## 待取得的证据

尚未拿到能在旧代码稳定失败的真实双指序列。已询问实际浏览器、断触发生于右手按下还是松开，以及是否伴随地址栏、全屏或长按菜单变化。待验证的路径包括捕获丢失、布局/暂停清理、浏览器原生取消；目前没有证据支持其中某一个。

为手机复现加入默认关闭的 `acceptance=1&touchTrace=1`。报告保存最近200项指针事件（移动节流100ms）、捕获状态、方向、浮动中心、模式、布局版本、视口、后台/窗口事件。记录不上传，刷新丢失；复现后需立即暂停并下载。开启此模式的对局不具备正式性能样本资格，普通游戏不安装这些监听或采样。

取得对应JSON后，应先把真实触发链路变成能失败的浏览器回归，再修改输入实现，并在目标手机确认。#21、#19及#16仍不能按修复通过关闭；#17继续等待。

`PLAYWRIGHT_CHANNEL=chrome pnpm test:browser-touch` 与 `PLAYWRIGHT_CHANNEL=msedge pnpm test:browser-touch` 各通过2项，约5秒；两者均新建独立测试配置。`pnpm check` 通过310项测试/18文件、三项类型检查、架构检查和正式构建。原有大包体积提示仍存在。最初受限沙箱的检查未继续输出，随后获准运行的完整检查正常完成；不是测试失败。

沿用用户已确认的完整审查基准 `ff1245c`，本次增量从 `38debe6` 起。
